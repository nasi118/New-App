# Baseline Report — 2026-08-22

Assessed at commit `69caff8` (branch `main`), before any changes on
`claude/canonical-foundation`. This records what was actually executed and
observed; nothing below is assumed.

## Repository shape

Two calculation implementations, as documented in `README.md`:

1. **Tax Advisory Pro** (JavaScript, `src/00-…24-*.js`, ~17k lines) —
   TY2025/TY2026 individual planning workbench. React 18 vendored UMD, no
   build step, `index.html` loads `src/*.js` in numeric order into shared
   global scope. Covers SE tax, S-corp compensation/FICA, §199A QBI
   (SSTB + wage/UBIA), NIIT with §1411 activity classification, Additional
   Medicare tax, retirement design (401(k)/SEP/defined benefit), SEHI/IRA
   interplay, MAGI phase-outs, itemized deductions, credits, multi-client
   profiles, scenario comparison, XLSX export, audit trail.
2. **`ai_tax`** (Python ≥3.11, ~2.9k lines) — audit-grade deterministic
   engine (`engine-0.1.0`): pure-function calculation with pinned immutable
   rulesets (2025 enacted, 2026–2030 provisional), stable line IDs, trace,
   diagnostics, built-in reconciliation as a release gate, immutable
   base/scenario lifecycle (`store.py`, `scenarios.py`), five-year
   projections, permanent verified Excel audit packages, and a constrained
   Tax Planning Analyst Agent (13 JSON-Schema tools, RBAC, tenant isolation,
   idempotency). Scope is deliberately bounded — see `docs/UNSUPPORTED.md`
   (no SE/QBI, no AMT, no Additional Medicare, no state returns, no
   carryforwards, nonrefundable-only CTC).

The two engines' scopes overlap on: ordinary tax, capital gain/qualified
dividend stacking, NIIT, CTC, itemized vs standard deduction, payments and
balance due. They diverge everywhere else (SE/QBI/S-corp only in JS; the
lifecycle/audit/reconciliation machinery only in Python).

## Failures observed (pre-existing on `main`)

1. **UI acceptance suite is stale relative to the 3.2 clients feature.**
   `tests/ui-acceptance.mjs` (written for the 3.0 redesign) assumes the
   legacy three-scenario seed. With the multi-client feature active, the
   default client loads one "Base — from profile" scenario, so:
   - `FAIL scenario cards render` (expects ≥3 `.tp-vcard`),
   - `FAIL calculator names its source scenario` (expects "Sole prop" in the
     drawer header),
   - hard abort at the cleanup step (`.tp-schead nth=3 button[title=Delete]`
     never appears — there is no 4th scenario column).
   The application behavior is correct; the test's fixture assumptions are
   outdated. This is a test-maintenance failure, not an engine failure.
2. **Documented example dirties the working tree.** `examples/output/`
   (store JSON, audit JSONL, xlsx package) is committed, and
   `build_example_case.py` regenerates it with new IDs, deleting the old
   package file. Generated artifacts in source control also conflict with
   the audit posture (issued packages are supposed to be immutable and
   hash-registered, not casually replaced by re-runs).

## Other observations recorded for later phases

- `src/23-clients.js:162` — client IDs are `"CLIENT-" + Math.floor(Math.random()*900+100)`:
  900 possible values, collision-prone, no immutable system ID (Phase 4).
- No CI of any kind (`.github/` absent) (Phase 3).
- `api/` (Vercel AI proxy) targets xAI Grok with `XAI_API_KEY`; the sibling
  deployment repo `AI-Tax-APP` has since moved its copy to the Anthropic
  Claude API — consolidation decision needed (Phase 9).
- No `docs/` capability matrix distinguishing the two engines' scopes; the
  JS workbench UI does not state which engine produced a number (Phase 2).
- Python store is JSON-file-backed behind a narrow interface (documented,
  deliberate); no tenant separation on disk (Phase 5).
- Import pipeline: documented and represented in the audit workbook, no
  parser implemented (documented, deliberate) (Phase 6).
- Rulesets carry `status` (enacted/provisional), `sources`, generator
  provenance; no reviewer/approval/checksum/supersedes fields yet (Phase 7).

## Environment limitations

- Sandboxed runner: outbound HTTPS goes through an egress-filtered proxy.
  `api.anthropic.com` is reachable; `*.vercel.app` and CDNs (jsdelivr) are
  not. Irrelevant to the test suites above (everything is vendored/offline),
  but live-deployment verification is not possible from this environment.
- Playwright uses the preinstalled Chromium at `/opt/pw-browsers/chromium`;
  the UI suite's documented global-install path does not exist here (the
  suite's own `PLAYWRIGHT_HOME` escape hatch covers this).
- `pip` runs as root in a disposable container (warning emitted; harmless).

## Baseline conclusion

The Python `ai_tax` core is in strong shape: all 55 tests pass, the
documented control matrix maps to real tests, and the end-to-end example
works. The JS workbench's engine passes its 41 golden tests. The gaps to
"canonical, production-ready" are exactly the ones this branch addresses:
no CI, no cross-engine contract, no machine-readable capability boundary,
fragile client identity, stale UI acceptance fixtures, committed generated
artifacts, and governance fields missing from rulesets.
